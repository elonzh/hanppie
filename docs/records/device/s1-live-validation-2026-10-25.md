已用当前生产 `AppSession` 建立真实会话；没有使用内存机器人或改写设备应答。按阶段串行连接、检查电量/数据新鲜度并关闭会话；动作阶段另验证车轮停稳。主机发现阶段曾被沙箱禁止 UDP 监听，经自动审核批准后正常发现；临时 Java 宿主入口和编译错误发生在设备连接前，不计作设备连接失败。没有开始 Android 验证。

## 已修复的实际不匹配

当前产品修复位于 robot-core，共用接收窗口还同步到 Python 客户端，保持协议入口/能力建模，不按型号硬编码共享 UI，也不修改冻结的冲突策略：

1. `RobotHealthStore` 只接收 `attr=00`，丢弃实机组合电池主题的 `attr=40`。现在该主题接受两种非响应属性，仍拒绝响应属性、错误节点/接收者及错误长度；模块报告保持原筛选。
2. 相机简化状态只接受 camera 节点 `01`，而本机由 HDVT `09` 转发。现在明确接受直发与转发，保留目的、CRC、属性、命令和长度要求；倍率、SD 和图像状态由同一服务更新。
3. 日期 getter 曾将二字节年份按十进制世纪解读，与实际 S1 线格式冲突。现与 setter 一样读取 uint16 LE，并保留日历、全零未设置和写后回读验证；未加入有歧义的双格式猜测。
4. 收音查询曾要求响应恰好两字节，拒绝实机四字节有效前缀。现在至少两字节，仍按原生非零布尔规则读取，不解释尾字段。

相关原始报文已经进入必要的协议回归向量。首批定向回归为核心 51 项中三项旧变焦时序失败，共享 22 项通过；该批自行失败退出，没有终止或遗留进程。失败源于测试用墙钟和实际调度假设“首帧必定是中间倍率”。改为测试内受控单调时钟后，同一范围 **核心 51 + 共享 22 = 73 项全部通过**，桌面 classes 通过；未改变产品变焦算法，也没有重复全量测试。修复后另以真实会话核对七项读取/校时/配置状态，均获预期结果，其中抗闪烁一项只确认残留读值 2，不代表恢复原值。

## 可靠接收窗口修复

后续透明抓包把首轮的视觉/音频/Lab 超时与原图中断定位到同一传输问题：设备恰好发满 100 个 type `03` 可靠包，主机未确认这些包。视频 type `02` 与非可靠遥测仍持续到达，不能因此把单个请求超时写成整机连接丢失。有效 UDP 缓冲为 4 MiB，扩大缓冲不是本次修复。

- 初始捕获中可靠 tick 为 16–808、步长 8；主机控制表偏移 16/18 均停在 8，原图只收到 71,483 字节。新会话中原 `attr=40` 视觉查询可直接获得 `c0 / 000000`，排除了必须改为 `attr=20` 的假设；视觉局部应答属性实验已撤回，生产 `AppSession` 和视觉状态机没有保留该改法。
- 第一版仅推进偏移 18，真实下载仍停在 100 个可靠包、70,490 字节。对照宿主将偏移 16 同样推进后，原图完整下载，后续两种视觉查询及音频查询均有返回。该轮对照改写已明确归档，不能冒充纯生产会话。
