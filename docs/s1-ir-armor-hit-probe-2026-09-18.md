## 已确认的事实

### 1. 受击事件的推送被显式门控（不是"模式"）

- `rm_ctrl.ArmorCtrl.hit_event_process` 只在 `sdk_hit_event_push_enable_flag` 为真时，才把
  `hit` 放进 SDK 推送（`src/hanppie/runtime/rm_ctrl.py:2398-2422`）；该标志默认 **False**。
- 事件推送还有独立的开关方法：`sdk_event_push_enable_flag_set(hit_flag='on'|'off')`。
- 受击事件载荷结构：`hit_index = (data[0] >> 4) & 0x0f`（装甲编号）、`hit_type = data[0] & 0x0f`。
- 红外受击是独立通道：`armor.ir_event_register()`（cmdset `0x3f` / cmdid `0x10`），
  对应主机侧 SDK 的 `IrHitEvent`（带回 `skill_id` / `role_id` / `recv_dev` / `recv_ir_pin`）。
- 条件等待接口：`ArmorCtrl.cond_wait(rm_define.cond_ir_hit_detection)` 等。

### 2. 主机侧观测能力的两处缺口（本次实测撞到的墙）

- **受击查询发不出去**：机内 `Armor.hit_event_query()` 的目标 receiver 是 16 位
  （`scratch_sys_id=905` / `system_id=801`），而主机侧 `connection.send_duss()` 的 receiver
  只接受单字节 → `ValueError: byte must be in range(0, 256)`（149 次连续失败）。
- **Lab 程序没有回传通道**：`LabRobot` 只抛 `telemetry` / `attitude` / `position` /
  `gimbal_angle` 四类事件，机内脚本的 `log_ctrl.print_msg` 输出不会到达主机侧 Python；
  改用"机内写文件 + 匿名 FTP 读回"时，`/data/workspace/irwatch.log` 等候选路径全部 `550`。

## 【重大结果】0012 我们自己发射的红外帧触发了装甲受击事件（01:13–01:20）

**结论先行**：树莓派的红外发射器（对着装甲）发出的、由"抓到的真帧"重建的波形，
让 S1 装甲**上报了红外受击事件**；编码结构已确定，可复现触发。

### 判据链（为什么这次能确定）

- 主机侧 SDK 的事件订阅实现是 `dds.add_subject_event_info` → `add_cmd_filter(cmdset, cmdid)`，
  **只加本地过滤器、不发订阅命令** ⇒ 受击事件是机器人**无条件推送**的 ⇒ 只要装甲登记了
  受击，主机一定能看到 `0x3f/0x02`（打击）或 `0x3f/0x10`（红外）帧。这消除了"事件没收到"
  这一类干扰。
- 事件帧实测：**`0x3f/0x10`（IrHitEvent），载荷恒定 `10 02 01 00 00`**；按 SDK
  `IrHitEvent.decode` 的字段顺序即 `(skill_id, role_id, recv_dev, recv_ir_pin)`。

### 标度扫描（01:13:58–01:15:35，每种 5 发）

把抓到的真帧按"载波宽度 × 比例"重放（其余不变），装甲接受情况：

| 载波比例 | 事件数 | 结果 |
| --- | ---: | --- |
| 0.700 / 0.750 / 0.800 | 0 / 0 / 0 | 拒绝 |
| 0.833 | 1 | 开始被接受 |
| 0.870 | 19 | 接受 |
| 0.920 | 25 | 接受 |
| 1.000（原样重放） | 21 | 接受 |

⇒ 装甲按**载波长度分档**解码，且接受窗口包含原样重放值（1.000）。
先前"必须反向补偿解调头展宽"的猜测**不成立**（0.833 以下全部落空）。

## 【模型修正 + 机内机制】02:00 前后

### 帧结构修正（两份真帧共同确定）

先前按单帧推出的"位 = 载波长短 + 第 4 单元后有分隔符"是**只有单个 1 位时的巧合**，已修正：

| 项 | 值（实测） |
| --- | --- |
| 帧结构 | **9 个等长单元**，每个 ≈1.81 ms：单元 0 = 整段载波（同步）；单元 1..8 = 数据位 |
| 位编码 | 单元内载波占空比：位 1 ≈64%（1149~1215 µs）、位 0 ≈35%（616~708 µs）；等价说法="紧邻长载波之前的间隙更短" |
| 帧长 | ≈16.3 ms |

依据：存档帧（22:29:54）与自发射帧（02:0x）都满足"每个单元 ≈1.81 ms、载波长 ⇒ 前一间隙短"。

### 弹丸载荷会变（两种位图）

| 位图 | 来源 | 样本 |
| --- | --- | --- |
| `0000 1000` | App/手动发射（存档） | 30 次一致 |
| `0000 1001` | 主机控制通道 `fire_infrared()` | 2 次一致 |

⇒ 载荷**不是常量**，随发射路径/参数变化（支持"机器人侧编码/参数影响红外帧"的方向，但字段语义待闭合）。

### 主机可直接下带参数的发射命令

机内 `set_cmd_fire(mode, count)` 的编码是 `(mode<<4)|count`，DUSS 为 `0x3f/0x51`（cmdset 63 / cmdid 0x51），
receiver `hdvt_uav_id=900` 在控制侧的 1 字节地址是 `0x09`。实测主机发 `0x3f/0x51` → `0x09`：
`payload=01`、`03`、`21` **三次全部 ACK**（`DirectAck(sender=9, receiver=2, cmdset=63, cmdid=81, payload=00)`），
但三次当次捕获没有抓到完整帧（发射与抓取的时间窗没对齐）⇒ 参数↔位图的映射未闭合。

### 机内处理机制（回答"完整机制"）

- **机内 `Armor` 的全部 API 只有 5 个**：`hit_event_register` / `hit_event_unregister` /
  `ir_event_register` / `hit_event_query` / `set_hit_sensitivity`（`rm_module.py:749-800`）
  ⇒ **没有任何红外解码、受理规则或装甲编码的配置接口**。
- `set_hit_sensitivity(k)` 实际配置的是 **voice_energy_* 一组参数**
  （`voice_energy_entry=500`、`exit=300`、`len_min=13`、`len_max=50`、`silence_wait_limit=6`、
  `peak_count_min=1`、`multi_peak_min/ave/final = 160k/180k/200k`，k 默认 5）
  ⇒ **"撞击受击"是麦克风能量型判定**（这也是"用机器人自己放响音"能做阳性对照的原因）；
  红外命中则是**解包判定**，不经过这组阈值。
- 红外帧的解码与受理发生在**装甲模块自身**（模块经 DUSS/串口挂在主控之外），主机与机内 Python
  都只能"读事件"，不能改受理规则 ⇒ **无法用机内代码让装甲接受任意红外指令**。
- 装甲编号与事件内容：`hit_index = (data[0] >> 4) & 0x0f` 映射到 6 块装甲
  （`ARMOR_BOTTOM_BACK/FRONT/LEFT/RIGHT`、`ARMOR_TOP_LEFT/RIGHT`，`rm_ctrl.py:2432-2472`）；
  红外事件的 `recv_dev` / `recv_ir_pin` 标识接收设备 ⇒ 装甲编码/编号会体现在这些设备字段上，

## 【成功复现 + 载荷↔命令字映射】23:08–23:11

用户重新摆好发射模块后（**改动的只是物理瞄准**），同一批老命令恢复触发，一次结构化实验拿到干净对照：

| 我发的命令字 | 帧数 | 红外事件 | 事件载荷 |
| --- | --- | --- | --- |
| 老字 `0000 1000`（第 1 轮） | ×4 | **16** | `10 02 07 00 00` ×16 |
| 机器人现字 `0000 1001` | ×4 | 5 | `90 02 07 00 00` ×3、`90 02 03 00 00` ×2 |
| 老字 `0000 1000`（scale 0.92） | ×4 | **15** | `10 02 07 00 00` ×15 |
| 老字 `0000 1000`（scale 1.05） | ×4 | **15** | `10 02 07 00 00` ×15 |
| 老字 `0000 1000`（第 2 轮） | ×4 | **16** | `10 02 07 00 00` ×16 |
| 机器人现字 `0000 1001`（第 2 轮） | ×4 | 6 | `90 02 07/02/03 00 00` |

**结论（新增事实）**：

1. **命令字第 8 位决定事件里的 `skill_id`**：`0000 1000` → `0x10`；`0000 1001` → `0x90`
   （0x10 与 0x90 只差最高位，与位图只差第 8 位完全对应）。
2. **`recv_dev` 会变**：老字全程是 `0x07`，机器人现字出现 `0x02/0x03/0x07`；
   对比 01:34 首次成功时的 `10 02 01 00 00`（`recv_dev=0x01`）⇒ **接收设备/装甲面板编号确实进入事件载荷**
   —— 这正是"装甲编号/编码会影响事件返回内容"的直接证据。
3. **同一轮里还打出了 12 个撞击事件**（`0x3f/0x02`，载荷 `530000000001010000c8c2`，全部聚集在第 1 轮发射的同一秒内）
   ⇒ 我们发的红外**也能触发撞击类事件**，两条事件通道都被打通。
4. **接受率是"爆发 + 冷却"结构**：1 分钟内 4 轮共 62 个命中后，紧接的一次复现轮 **0 事件**。
   结合早先"20~30 秒连发只第 1 发被受理"的观察 ⇒ 装甲在一次密集命中后会短暂拒收，
   **操作上应当：一轮 4~5 发（能拿到 ~15 个事件），轮间间隔 2~3 分钟**。

**前面连续失败的原因定论**：发射电路、时序、强度都正常（有回听与遥测证据），
**唯一致因是物理瞄准**——用户重新贴合模块后即恢复；其余假设（模式、开启、编码错误）均被排除。

### 装甲编号（SDK 权威语义，非推测）

### 血量与复活：找到的是**桥接键**，线上格式仍未还原

App 静态分析工作区（`.hanppie/app-analysis/2026-09-08/`）解包结果里，`protocol/key-index.json`

| 桥接 key | id | 类型 | 访问 |
| --- | --- | --- | --- |
| `DJIRobomasterSystemRevive` | 83886089 | Long | **Action** |
| `DJIRobomasterSystemKill` | 83886088 | void | Action |
| `DJIRobomasterSystemCurrentHP` | 83886117 | Float | Read\|Write |
| `DJIRobomasterSystemTotalHP` | 83886118 | Float | Read\|Write |
| `DJIRobomasterSystemCurrentBullets` | 83886119 | Long | Read\|Write |

App 侧调用形态（反编译 C#）：`Command.performAction(DJIKeys.DJIRobomasterSystemRevive, param, null)`；

⇒ 说明机器人**会把血量推上来**，App 只做显示。

**但这些是 Unity↔RobotService 的桥接键，不是线上命令**；key→线上帧的映射在原生 codec

⇒ 结论：**血量在当前（非对战）会话里不上报**，很可能只在 App 的对战/单机对战模式下推送。

### 终极目标（自定义红外载荷 + 自定义处理逻辑）可行性

| 环节 | 可行性 | 依据 / 障碍 |
| --- | --- | --- |
| 编码并发射自定义载荷 | **可行** | 命令字 → `skill_id` 直接映射；发射侧完全由我们控制（38 kHz + 9 单元帧） |
| 自定义接收端解码/受理 | **不可行** | 解码与受理在装甲固件；机内 `Armor` 仅 5 个 API、无解码配置 |
| 主机侧自定义处理逻辑 | **现在就能做** | 监听 `0x3f/0x10` 即得 `skill_id/role_id/recv_dev`，可驱动任意主机行为（今天已验证 116 次事件） |
| 机内自定义处理逻辑 | **应当可行，但当前卡住** | 机内 Lab 脚本可 `cond_wait('ir_hit_detection_*')` 并执行任意动作；但本项目上传的 Lab 程序**没有真正执行**（灯探针证伪），需改走已验证的 Lab/bridge 路径 |
| 控制血量/复活 | **待打通** | 桥接键已定位（Read/Write/Action），线上帧格式未还原；**最快路径：抓官方 App 点"复活"时的报文** |

**分三步走的方案**：① 主机侧事件驱动逻辑（今天即可用）；② 打通机内 Lab 执行 → 机内自定义逻辑；
③ 复原复活/血量线上格式（嗅探官方 App 或继续反汇编原生 codec）→ 完整闭环。

## 【复活指令：从原生符号反汇编到实机验证】23:40–23:50

### 定位过程（不猜）

1. App 桥接键里有 `DJIRobomasterSystemRevive`(83886089, Action) —— 但 key-index 明确"不是线上命令表"；
2. 原生符号表里找到实现：`dji::sdk::RobomasterSystemAbstraction::ActionRevivePlayer`（`0x6a8380`），
   同族还有 `ActionKillPlayer`(`0x6a7e40`)、`ActionResetBarrelOverheat`(`0x6aa030`)；
3. 用 `otool -tV` 反汇编该函数，看到它构造 `dji::core::DJIRMResetGamePack`：
   ```
   movl  $0x20a3f01, -0x98(%rbp)     ## → 字节 01 3F 0A 02（类型 / cmdset 0x3F / cmdid 0x0A / 02）
   movb  $0x9, -0x92(%rbp)
   movb  $0x0, -0x94(%rbp)
   callq dji::sdk::BaseAbstraction::SendActionPack<dji::core::DJIRMResetGamePack>
   ```
   ⇒ **线上命令 = DUSS `cmdset 0x3F` / `cmdid 0x0A`**，payload 为该动作的 2 字节参数。

### 实机验证

| 发送 | 结果 |
| --- | --- |
| `0x3f/0x0a` → receiver `0x28` | **rejected with 224** |
| `0x3f/0x0a` → receiver `0x09`（= 机内 `hdvt_uav_id`) | **DirectAck(cmdset=63, cmdid=10, payload=00)** ✓ |

⇒ **复活 = `0x3f/0x0a` → receiver `0x09`**（与发射命令同一条控制通道）。
**实效验证**：发出复活命令后立刻打 4 帧，红外事件（`1002070000`）与撞击事件（`530000000001010000c8c2`）成对正常上报
⇒ 复活后命中立即恢复被受理（与"命中耗尽后拒收"的现象一致；但"是复活还是时间恢复了接受"尚未做对照组，
标为**待严格区分**）。

### 血量的读取路径（未打通，但路径明确）

血量是**属性式**访问：反汇编里 `ActionRevivePlayer` 之外，属性代码只做
"拼字符串 + 传 key id"（例如 `CurrentHP` 站点附近是 `CurrentHP`/`ParamTotalHP` 字符串 + `0x05000025`/`0x05000026`），
由 SDK 的通用属性通道收发 ⇒ **线上帧格式不在这个二进制的数据段里**。
经验法（记录全部 DUSS 帧 1545 条、含命中）**没有发现随命中跳变的字段** ⇒ 血量很可能只在
App 的**对战/单机对战模式**下推送。下一步：① 在对战模式下重做全帧对比；② 或抓官方 App 读取血量时的报文。

### 修正一条先前结论

`role_id` 与受击侧的对应：早期观察到左=0x02 / 右=0x04，但复活后这一轮（发射器对着右侧）事件仍是 `role_id=0x02`
⇒ **不能把 `role_id` 直接当作"左右侧"**，它与受击侧的对应关系**待更多样本**，此前文档里的表述已按此修正。

### 通用结论（对"自定义处理逻辑"的意义）

1. `0x3f` 段是**成对的属性读写通道**（偶=读、奇=写），ACK payload 即值；

## 【技能通道打通：receiver 0xA9 + 技能信息可读】01:35–01:50

### 关键纠正：技能/Lab 命令走另一个 receiver

他们已验证的 Lab 命令用的是 **`send_duss(sender=0x02, receiver=0xA9, attr=0x40, cmdset=0x3F, …)`**：
`0x3F/0xA3` = Lab 程序控制、`0x3F/0xAB` payload `01` = 启动、`0x3F/0xBA` payload `00` = 停止。
**我此前把技能命令发往 receiver `0x09`（控制通道）⇒ 一律 224**，通道用错。

### 打通证据：`0x3F/0xA8` 读自定义技能信息

```
发送：receiver 0xA9, attr 0x40, 0x3F/0xA8, payload {"list":[]}
返回：0x3F/0xA8 payload = 00 01 00 | 6261376463313561393663383466343038653433366337626361373136616536 | 437573746f…
                              ↑ "ba7dc15a96c84f408e436c7bca716ae6"（32 位 hex GUID）      ↑ "Custo…"（JSON）
```

⇒ **机器人返回已安装自定义技能的 GUID（JSON），即"Lab 脚本作为技能"在本机确实存在** ✓。

### 技能控制包布局（反汇编 `SendSkillControlPack`，34 字节）

```
cmdset/cmdid：movw $0x3f01 → cmdset 0x3F；movb $-0x5d → cmdid 0xA3
payload 首字节 = (参数 << 4) | keyByte；keyByte：枚举键 0 → 0x0B，键 1 → 0x0C
```

### 由此得到的完整官方路径（用于终极目标）

1. 生成脚本 + 身份（`guid = token_hex(16)`、`sign = token_hex(8)`）→ 经 FTP 上传 DSP（已验证可用）；
2. 用 `0x3F/0xA3`（receiver 0xA9、attr 0x40）注册/安装为技能（带 SkillIndex）；
3. `0x3F/0xAB` payload `01` 启动、`0x3F/0xBA` payload `00` 停止；
4. 用 `0x3F/0xA8` 读回技能信息校验；用 `0x3F/0xA4`（机内脚本消息通道）确认脚本真的在跑。
